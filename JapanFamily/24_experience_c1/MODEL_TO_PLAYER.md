# モデルと表示・行動の対応

| プレイヤーの操作・表示 | 実際に使う状態と処理 | 効果の区分 |
|---|---|---|
| 父親本人のプロフィール | A persons / parents、家庭生成API。観察者をfatherに固定 | 統計参照＋条件付き抽選・移送仮定 |
| 妻の仕事・復帰相談 | 別person_id。本人の対案を記録し、保育申請と分担を確認できた場合のみ母本人のrequest_returnをAへ送信 | 合意ルールはC1人物シナリオ、就業結果はA未検証モデル |
| 妻の休日の希望 | 安定した独立NPC方針。プレイヤーには本人の発言だけを返す | 架空の人物設定。心理尺度ではない |
| 育児を2時間引き受ける | 父の休日枠−2時間、母の既存育児を2時間代替。母は独立した休息・散歩の予定を実行し、wife_actionsへ記録 | 時間の再配分シナリオ。Aの給与・Bの発達には係数を入れない |
| 抱っこ、絵本、玩具、床遊び | 月齢条件、持ち物、費用のLedger支払、既存の育児枠の一部を活動へ割当 | 価格・所要時間は明示的ゲーム見積もり |
| 公園、ひろば、旅行 | 休日枠、費用、必要な配偶者合意。訪問先・関係人物・反応をexperienceへ記録 | 施設・旅行商品は仮。実在の空き枠・利用資格を推定しない |
| 保育見学 | 同意した仮の見学枠への訪問経験。申請とは別 | 見学自体で入園率を加算しない |
| 子どもの活動反応 | Bの当時の潜在特性・短期状態・実月齢を参照。C1の別ハッシュ乱数で活動の刺激量、経験頻度・直近性から短期反応を抽選 | **新たな未校正短期シナリオ**。医学的・心理学的な因果効果ではない |
| 同じ絵本・場所への再訪 | inventory、context、前回experience_id、経過日数と曝露回数 | 手続き的な慣れの計算仮説。自伝的記憶や愛着の推定ではない |
| 毎月の予定 | 次月に同じ活動を予約。再見積もりし、資金不足や時間不足なら延期理由を残す | 日々の育児頻度を測定したという意味ではない。月1回の体験枠 |
| 勤務・休業・求職 | 既存Game.request→A step。受理・不成立、実働、給与の発生と振込を分離 | Aの未検証就業シナリオ。職場の現実の承認確率とは異なる |
| 保育申請、児童手当、親族支援 | 既存A API。希望と利用実績・支援の確保を区別 | 制度・選考・資格の未検証範囲を継承 |
| 支出方針 | 既存Aのset_spendingへ0.9を送信 | 通常消費への係数シナリオ。全支出の10%節約ではない |
| 預金振替 | cash⇄termのnative Ledger transfer。純資産は保存 | 解約条件・手数料・金利運用は未実装 |
| 子どもの普段の観察 | 既存Bのfather player view。父が観察し得た報告だけを表示 | 観察感度・行動確率はBの未校正モデル |
| 暮らしの文章 | 構造化されたplan / experience / transaction / native decisionのテンプレート変換 | LLMによる補話なし。人名以外に蓄財経緯、病気、天候、能力等を創作しない |

## 会計と時間

C1追加費用は、Aの完了チェックポイント間に `Ledger.expense_due` と `pay` を使って計上する。費用発生・未払金・支払を記録し、純資産恒等式と現金恒等式を検査する。支払能力がない予定を借金で強行せず、未実行として保存する。C1の独立finance ledgerを次期Aの開始口座へ引き継ぐ。**Aの当月journalだけを見てもC1の期間間費用は含まれない**ので、再集計時はC1 financeも併合する。Aの既存仕訳へ偽装して混ぜない。

計画枠はA前月の週配分×4週、初回は通常勤務を使う明示的仮定。日付別の実測勤怠ではなく、正確な日々の衝突までは判定しない。遊びは既存の育児枠を置き換え、二重に自由時間を消費しない。外出等は休日枠を使用し、育児分担は同じ子の監督を父へ移す。確保した活動ブロックの中で早めに遊びを切り上げることもあるが、枠の長さを実測したプレイ時間とは扱わない。

## 時間進行と保存

1か月を約3.33秒の3段階で表示。段階1・2では実際のC1予定を実行し、段階3で既存A/Bを次の暦月境界へ進める。日単位の新しいAエンジンに置き換えていない。月の途中であるかのような架空の日付は付けず、ログは年月を中心に示す。途中出生ではBの実日齢・24か月誕生日を維持する。

保存対象はA/B checkpoint、予定、合意、持ち物、費用・時間、反応・経験、関連ID、段階、速度、停止状態、段階内の経過時間。表示GETは乱数も状態も消費しない。サーバの操作は候補状態に対して実行し、成功時にまとめて反映。二重入力はrevisionで防ぐ。UI側は前の操作が処理中でも次の入力を黙って捨てず、処理待ちにする。

## 非公開状態

Bのlatent_state、emotion_regulation、成長の潜在順位、発達frailty、反応確率、妻NPCの内部方針コード、Aの未完了forecastはプレイヤーAPIから返さない。C1反応確率は信頼された検証用experienceのresearch_onlyにのみ保存。プレイヤーは観察反応、発言、完了済み家計、希望と結果だけを見る。
